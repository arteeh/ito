Evidence labels:

## Findings, highest priority first

### P1-1 For robots without `head_angles`, the pilot's head turn is applied twice. Microduck in VR or desktop is affected. **Reproduced (numerically, through the real code)**
- Where: `ito/app/pilot.py:198-209` (`_anchor`) and `ito/app/pilot.py:323-331`, which uses it for SLAM. The cause is `drivers/microduck/camera.py:116-123`, whose metadata has no `head_angles` and no `body_yaw`.
- Scenario: Microduck uses SLAM automatically (it has no depth or pose). The pilot looks 30° left and the robot head follows. The SLAM camera pose then includes the 30°. `_anchor` only removes head and body rotation when the metadata carries them, so the renderer draws `camera_pose @ pilot_head` and shows a 60° view. I called `Pilot._anchor` with a 30° camera and a 30° head. It rendered a 30° view with `head_angles` and a 60° view without them.
- Impact: The scene swings a second time whenever the robot head or body catches up with the pilot. That is the motion-sickness loop the vision exists to prevent, on the first real robot. `e2e/microduck.py:286` only checks the CPU flat-video fallback, so the e2e suite cannot see this. MuJoCo always sends `head_angles` and hides it.
- Smallest fix: In the Microduck `Track`, attach the measured `head_yaw`, `head_pitch + neck_pitch` and `base_yaw` from the latest `robot.state` (the one nearest the receive time). In `Pilot._session`, keep the flat feed instead of the 3D anchor when a robot that advertises a moving head sends frames without them. Longer term: replace the pan/tilt tuple with a measured camera-in-body `Pose` per exposure. That works for 4-DOF necks, humanoids and drones.

### P1-2 Microduck video timestamps break the RGB/metadata join, and about half the frames are dropped. **Reproduced**
- Where: `drivers/microduck/camera.py:114` uses `round(seconds * 90000)`. `drivers/mujoco/camera.py:84-86` instead rounds to millisecond multiples of 90 ticks, with a comment explaining why.
- Scenario: I sent both schemes through real aiortc VP8, the default codec, and applied the pilot's join key `round(pts * time_base * 90000)` (`ito/app/frames.py:61`). MuJoCo matched 60/60 frames. Microduck matched 35/60 in one run and 28/60 in another, because received pts came back 1 tick off (4206 sent, 4205 received). H.264 matched 60/60 for both.
- Impact: `FrameJoin` discards unmatched frames. The pilot gets about half the frame rate for video and SLAM, and long unlucky runs hit the 5 s "No synchronized camera frames" reconnect.
- Smallest fix: Move the millisecond-tick pts rule into one helper in `ito.driver` and use it from both drivers.

### P1-3 Anyone who sees one connection on the LAN can recover the pairing code offline. **Reproduced**
- Where: `ito/link/pairing.py:34-40`, `ito/driver/pairing.py:93-112`, and `ito/link/signaling.py:65-77` (plain HTTP).
- Scenario: A passive observer on the LAN or Wi-Fi records one `/pairing` nonce and the following `/offer` (SDP and proof). Trying all 10^6 codes against the real `proof()` with a 3 KB SDP recovered the code in 1.4 s on one core.
- Impact: The code is persistent. The attacker can pilot the robot whenever the pilot is disconnected. The answer proof uses the same code, so they can also impersonate the robot (MITM, by rewriting the DTLS fingerprint) on later connections. The driver listens on `0.0.0.0` by default (`ito/driver/cli.py:18`).
- Smallest fix: Use a PAKE such as SPAKE2, so a transcript does not allow offline guessing. Alternatively, on the first successful pairing, send a random 128-bit per-pilot secret over the DTLS data channel, use it for all later proofs, and make the 6-digit code single-use.

### P1-4 The bundled torch has no kernels for current NVIDIA GPUs, so SLAM silently drops to flat video on RTX 50-series. **Source plus public reports**
- Where: `pyproject.toml:41-45` (`torch==2.5.1` from the cu124 index), `ito/build.py:113` (`TORCH_CUDA_ARCH_LIST` stops at `9.0+PTX`), and README (CUDA 12.4).
- Scenario: Any Blackwell GPU (sm_120). The torch 2.5.1 cu124 wheels contain sm_50 to sm_90 only, and Blackwell needs CUDA 12.8 or later. The error is caught and the pilot sees the flat feed with a CUDA error. CuPy 13.6 with NVRTC 12.4 also cannot target sm_120, so RGB-D falls back to the CPU.
- Impact: The main target (Windows, NVIDIA first) loses the product's core feature on current-generation cards.
- Smallest fix: Move the `slam` extra to torch 2.7 or later with cu128 and CUDA 12.8, add `12.0` to the arch list, and have `release/windows.py check()` print `torch.cuda.get_arch_list()`. Verify on an RTX 50 card.

### P1-5 One refused or slow Microduck RPC faults the driver until it is restarted. **Source**
- Where: `drivers/microduck/adapter.py:209`, where every RPC has a deadline of `input_timeout` (0.25 s). `drivers/microduck/remote.py:79-80` turns `accepted: false` into `RemoteError`. `adapter.py:106-117` (`_guard`) records the error permanently, after which `_check` raises in every `apply`, `telemetry` and `media_tracks` call.
- Scenario: robotd refuses `robot.move` or `robot.pose` while the duck is `fallen` or `picked_up`, or one answer takes longer than 250 ms on the robot's weak CPU.
- Impact: The robot is stopped, which is safe. But the driver stays in `fault`, new offers fail with "unable to negotiate media", and the pilot loops reconnecting until someone restarts the driver. That conflicts with "every feature handles its failures".
- Smallest fix: In `_commands`, catch `RemoteError` and `TimeoutError` per RPC, go neutral, report the reason in telemetry, and keep the loop running. Only `Remote.fail` (connection loss) should be fatal.

### P2-1 The Windows build's Python 3.12 has a 15.6 ms `time.monotonic`. **Source plus CPython docs (not run on Windows)**
- Where: All timestamps use `time.monotonic`, for example `ito/desktop/input.py:174,186`, `ito/xr/dispatch.py:30`, `ito/app/pilot.py:405` and `ito/link/peer.py`. The release pins 3.12 (`release/windows.py:44`). CPython 3.13 is the release that moved Windows `monotonic` from GetTickCount64 to QueryPerformanceCounter.
- Impact: Input is sampled at 90 Hz, so gamepad look sees `dt` alternate between 0 and about 15.6 ms. That makes the view rotation judder, a comfort problem on the main platform. The XR tracking query time jitters by about ±15 ms, so the pose sent to the robot jitters. Equal `capture_time` values are rejected by the driver as stale (`ito/driver/server.py:112`). Latency metrics are quantized.
- Smallest fix: Add one `ito.clock.now()` built on `time.perf_counter`, which is QPC on Windows (system-wide) and CLOCK_MONOTONIC on Linux (the same clock as today). Use it for every wire, input and render timestamp. Confirm on Windows with `runtime\python.exe -c "import time;print(time.get_clock_info('monotonic'))"`.

### P2-2 Depth frames share the reliable control channel with Status and command acknowledgements. **Hypothesis**
- Where: `ito/link/peer.py:36,286-297` and `drivers/mujoco/camera.py:49-54`. Depth allows up to about 1 MB of base64 zlib per frame (`ito/protocol/__init__.py:121`).
- Scenario: A real, noisy depth camera at VGA and 30 fps over aiortc's pure-Python SCTP on Wi-Fi.
- Impact: Head-of-line blocking delays the 10 Hz Status. Past 2 s the pilot tears down the link ("Driver status lost"). E-stop confirmation in the overlay arrives late. Synthetic MuJoCo depth compresses too well to show this.
- Smallest fix: Send `FrameMetadata` on its own unordered data channel with `maxPacketLifeTime`, and keep `control` for small messages.

### P2-3 XR sorts the whole splat buffer once per eye. **Hypothesis (needs GPU timing)**
- Where: `ito/render/renderer.py:157-173`, called per eye from `ito/xr/window.py:152-168`.
- Impact: 1M splats is the default on NVIDIA cards with 8 GB or more (`ito/reconstruction/__init__.py:23`). That is 98 bitonic passes of about 16 MB each per sort, two sorts per frame, about 280 GB/s at 90 Hz, before rasterization and while MASt3R shares the GPU. Mid-range cards would miss the frame budget.
- Smallest fix: Sort once per frame from the mid-eye pose and reuse the order for both eyes, and lower the XR default budget. Measure with `GL_TIME_ELAPSED` queries.

### P2-4 The viewpoint moves in steps at camera or SLAM rate. **Hypothesis**
- Where: `ito/app/pilot.py:198-209` replaces `robot_camera` atomically, and the renderer uses it directly.
- Impact: While the robot drives, the eye position jumps at 30 Hz, or 2–10 Hz with SLAM (about 6 cm per step at 0.3 m/s), while the display runs at 90 Hz. That judder is noticeable in VR. I could not measure it here, because llvmpipe displays at only about 15 Hz.
- Smallest fix: Interpolate the anchor translation in the render thread with one update interval of delay.

### P2-5 The release has no project licence and no third-party notices, and it ships GPL codecs. **Reproduced on the Linux wheels; Windows wheels not inspected**
- No `LICENSE` exists for Ito.
- The PyAV wheel bundles `libx264` and `libx265` (GPL), with FFmpeg reporting "LGPL version 3 or later". SDL and pygame-ce are LGPL. torch brings NVIDIA CUDA libraries.
- `ito/build.py` adds an attribution file only for MASt3R.
- MASt3R is CC BY-NC-SA, so the bundle cannot be sold. That matters for the Steam idea in the transcript.
- Smallest fix: Add a `LICENSE`. Have `release/windows.py` generate `THIRD_PARTY_NOTICES` from every `dist-info/licenses` and from `models/`, with source offers where the (L)GPL requires them. The owner needs to decide the NC question.

### P2-6 Anyone on the LAN can lock the pilot out of pairing. **Reproduced by the project's own e2e**
- `ito/driver/pairing.py:96-99` counts failures globally. `e2e/webrtc.py:140-145` shows the correct code refused with 429 after nine wrong guesses.
- Any host that keeps sending 10 bad offers per minute keeps the real pilot refused.
- Smallest fix: Count failures per remote address, which is TCP so it cannot be spoofed, with a much higher global ceiling.

### P3, lower priority
- **The right trigger is both "click panel" and "open beak".** `ito/xr/window.py:57` uses the trigger to click the panel. `drivers/microduck/adapter.py:188-190` maps `right_trigger` to the beak, so clicking Resume or Mute in VR drops whatever the duck carries. **Source.** Fix: zero robot-bound trigger axes while the pointer is on the panel.
- **The XR panel can never be hidden.** `ito/xr/window.py:249-258` always draws it. From the panel capture geometry, the 90%-opaque status window covers about 20°×20° just left of forward. **Reproduced** (capture). Fix: hide it unless a controller points at it, or add a menu toggle.
- **An RGB-D worker failure tears down the robot link.** `ito/app/pilot.py:340-343` reconnects, which disarms the pilot. SLAM failures keep the link and show flat video. **Source.** Fix: use the same flat fallback and restart the worker.
- **The SLAM 3D/flat switch has no hysteresis.** `ito/app/pilot.py:321-336` flips the view each time tracking crosses the 2 s threshold, so the pilot can see flicker at the edge of tracking. **Hypothesis.**
- **The driver relies on the pilot to require Resume.** A fresh connection, or a driver restart, accepts deadman input immediately (`ito/driver/server.py:122-123,249-253`). The e-stop latch does not survive a driver restart. The official pilot gates this with `armed`. **Source.** Fix for defence in depth: start every connection "stopped".
- **The driver watchdog is unsupervised.** `ito/driver/server.py:191-228` is a single task with no done-callback. An unexpected exception, for example from `peer.close()`, would silently stop input-timeout enforcement. **Hypothesis.** Fix: add a done-callback that goes neutral and exits.
- **The standalone MuJoCo driver plays a constant 440 Hz tone as its microphone by default** (`drivers/mujoco/cli.py:37`). The pilot hears a beep, a test-signal default, which goes against the `AGENTS.md` "no mock paths" rule. Fix: default to `none`.
- **e2e harness: the offline audit treats this host's own LAN address as external** (`e2e/offline/sitecustomize.py:10-12`). It does so when the hostname does not resolve to that address, which made `e2e/slam.py` fail here. It passed after I added the address to `/etc/hosts`. **Reproduced.** Fix: collect local addresses with `psutil.net_if_addrs()`.
- **Ruff fails.** `ruff check` reports 4 E501 in `e2e/stream.py:69,70,174,176`, and `ruff format --check` flags `e2e/sample_scene.py` and `e2e/stream.py`.
- **`VISION.md` conflicts with `AGENTS.md:17`**, which says `AGENTS.md` is "the only other prose". Either allow the file there or keep it off `main`.
- **On Linux from source, a killed pilot leaves the simulated driver running** (`ito/app/sim.py`, with no parent-death handling). Windows is covered by the job object in `release/ito.c`.
